Facts worth remembering
  - Vault: ~/.local/share/auth/vault.gpg on cpbee, gpg key auth-vault; `ssh -t cpbee auth unlock` once per 8 h.
    The secret key is backed up off-site (Chris, 2026-11-04).
  - Mailutils reads `#` in a netrc as a word, so the rendered ~/.netrc has no marker lines; the tickets file may.
  - tvmail asks for imap://, so the vault record carries imap, imaps, smtp and smtps; each is rendered under
    cpbee.cmnet and bare cpbee.  The apps match the host exactly as their own config spells it.
  - Radicale is a separate login from the cpbee account.
  - The pre-commit scan flags URL-shaped examples: tag them `# allowlist secret`.

Notes for the two open decisions
  admin line: `chris *@cpbee.cmnet chris admin` says "the login chris, on ANY service on cpbee, is an admin".  It is
    there because Floyd's admins= lists "chris" (email !claude, talk).  `identity check` compares Floyd's lists to
    the admin flags.  With logins unified on chris, one wildcard admin line is the simplest; the alternative is to
    put `admin` on explicit lines (irc, imap, http ...).  Recommendation: keep the wildcard.
  gpg agent: the vault and its agent belong to the chris user on cpbee; clients reach it via `ssh cpbee auth ...`.
    The webterm change (web services moved to a no-login system user) does not touch it.  The question only arises
    for things that run as OTHER users (Floyd's service, Michelle) and want a secret: they cannot unlock chris's vault.
    Options: (a) they get nothing from the vault, setup scripts render their files once while chris is unlocked;
    (b) a root-owned broker on cpbee that answers `auth get` for named records.  Recommendation: (a) until phase 4.
